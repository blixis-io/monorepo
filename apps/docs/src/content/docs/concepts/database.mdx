Blixis stores relational data in **Neon Postgres**, reached from Workers through **Cloudflare Hyperdrive**. `@blixis/database` owns connections. Modules never open connections or read bindings themselves: they get the database as a service. The query layer is [Drizzle ORM](https://orm.drizzle.team) on the `pg` driver (ADR 0006).

## Enabling the database

Add the platform module to your app. It provides the [`DATABASE`](/api/database/variables/database/) service and the `blixis.database` capability.

```ts
import { databaseModule } from '@blixis/database'

const app = createBlixis({ modules: [databaseModule(), contentModule()] })
```

By default, it reads the connection string from the `HYPERDRIVE` binding. Pass `databaseModule({ binding: 'OTHER' })` to use another binding.

## Using it in a module

Declare your tables in your module's own Postgres schema. Then resolve `DATABASE` from the request's services:

```ts
import { DATABASE } from '@blixis/database'
import { eq } from 'drizzle-orm'
import { pgSchema, text, uuid } from 'drizzle-orm/pg-core'

const content = pgSchema('content')
export const entries = content.table('entries', {
  id: uuid('id').primaryKey().defaultRandom(),
  title: text('title').notNull(),
})

routes.get('/:id', async (c) => {
  const db = c.var.services.get(DATABASE)
  const [entry] = await db.select().from(entries).where(eq(entries.id, c.req.param('id')))
  return c.json(entry)
})
```

- **One database per request.** The service is request-scoped (ADR 0005). It connects on the first query and is closed automatically when the request, queue message, or cron job ends. Never keep it in module-level variables.
- **Full Drizzle API.** `DATABASE` is Drizzle's own database type, not a Blixis wrapper, so the whole typed query builder and `sql` template are available.

## Transactions

Run multi-statement work with [`withTransaction`](/api/database/functions/withtransaction/). It commits when your function resolves and rolls back when it throws:

```ts
import { DATABASE, toTransactionScope, withTransaction } from '@blixis/database'

const entry = await withTransaction(c.var.services.get(DATABASE), async (tx) => {
  const [row] = await tx.insert(entries).values(input).returning()
  await tx.insert(entryVersions).values({ entryId: row.id, version: 1 })
  return row
})
```

- **Isolation:** the default is `read committed`. For `serializable` work, use [`withRetryableTransaction`](/api/database/functions/withretryabletransaction/), which reruns your function after a serialisation failure or deadlock. Your function must be safe to run again.
- **No nesting:** `withTransaction` takes the database, not a transaction. Pass `tx` down to helpers instead. For an explicit savepoint, use Drizzle's `tx.transaction(...)`.
- **Across packages:** hand [`toTransactionScope(tx)`](/api/database/functions/totransactionscope/) to APIs that accept a `TransactionScope`, such as transactional events.
- **Errors:** driver errors are translated (see below). Errors your function throws, such as `NotFoundError`, pass through unchanged.

<Aside type="note">
Hyperdrive pools connections per transaction. Use `SET LOCAL` inside a transaction instead of `SET`, and don't hold a transaction open while calling other services.
</Aside>

## Errors

`withTransaction` already does this for you. For queries outside a transaction, pass driver errors through [`translateDatabaseError`](/api/database/functions/translatedatabaseerror/) before rethrowing:

| Postgres error | Blixis error |
|---|---|
| Unique violation (`23505`) | `ConflictError` with `details.constraint` |
| Foreign-key violation (`23503`) | `ConflictError` |
| Serialisation failure, deadlock, timeouts, lost connection | `InfrastructureError` with `retryable: true` |
| Anything else | `InfrastructureError` |

<Aside type="caution">
Drizzle's own error message includes the query **parameters**, which can hold user data. `translateDatabaseError` drops them and redacts connection strings. Don't log or rethrow raw driver errors.
</Aside>

## Migrations

Each module owns its Postgres schema and ships SQL migrations in its definition:

```ts
import { defineMigration } from '@blixis/contracts'

export const createEntries = defineMigration({
  id: '0001_create_entries',
  up: /* sql */ `
    create schema content;
    create table content.entries (id uuid primary key default gen_random_uuid(), title text not null);
  `,
})

export const contentModule = defineModule({ meta, migrations: [createEntries] })
```

- `pnpm db:new <module-dir> <name>` scaffolds the next file. `drizzle-kit generate` can propose the SQL from your Drizzle schema, which you then review and paste in.
- `pnpm db:migrate` applies pending migrations in module order, each in its own transaction, and records them in `blixis.migrations`. `pnpm db:status` shows what is applied, pending, or blocked.
- **Never edit an applied migration.** Its checksum is verified, and the run is blocked. Add a new migration instead, and change schemas expand/contract style (add, backfill, switch, then drop later).
- Migrations never run inside the Worker. CI applies them before deploying.

Full conventions: `docs/conventions/migrations.md` in the repository.
