Authentication answers *who is the actor?*; authorization answers *may this actor do this?*. Blixis keeps them apart: requests carry an **actor**, and services ask the **authorization service** before acting.

## Actors

[`Actor`](/api/contracts/type-aliases/actor/) is a union:

| `type` | Who | Notes |
|---|---|---|
| `user` | a signed-in user | `userId` |
| `apiToken` | a personal API token | owner's permissions, limited to `scopes` |
| `deliveryKey` | a space's delivery or preview key | content delivery only |
| `system` | platform code (queue consumers, cron, workflows) | denied unless a check sets `allowSystem` |
| `anonymous` | no credentials | [`ANONYMOUS_ACTOR`](/api/contracts/variables/anonymous_actor/) |

Use [`actorId(actor)`](/api/contracts/functions/actorid/) for logs and metadata — it never contains secrets.

## Declaring permissions

```ts
import { definePermission } from '@blixis/contracts'

permissions: [
  definePermission({
    id: 'seo.read',
    description: 'Read SEO metadata',
    defaultRoles: ['admin', 'editor', 'viewer'],
  }),
  definePermission({ id: 'seo.write', description: 'Edit SEO metadata', defaultRoles: ['admin', 'editor'] }),
]
```

- `scope` is `'space'` (the default) or `'organization'`. Space permissions come from organization and space memberships. Organization permissions come from organization memberships only.
- `defaultRoles` grants the permission to [system roles](#roles). `owner` always holds every permission, so a permission without `defaultRoles` is owner-only unless a custom role grants it.

IDs are `<module>.<action>` or `<module>.<resource>.<action>`, lowercase, with your module's namespace first. Each namespace belongs to **one** module: if another module already declared `seo.*` permissions, declaring `seo.write` in yours fails startup. Duplicate IDs fail too, naming both modules.

## Roles

Roles group permissions. They are configuration, owned by `@blixis/permissions`:

| Role | Permissions | Assignable to |
|---|---|---|
| `owner` | every permission | organization memberships |
| `admin` | permissions listing `admin` in `defaultRoles` | organization and space memberships |
| `editor` | permissions listing `editor` | organization and space memberships |
| `viewer` | permissions listing `viewer` | organization and space memberships |

Organizations can also define **custom roles**: a name plus a list of permission IDs, stored per organization. A membership stores a system role key or a custom role ID. `GET /api/v1/permissions` lists the catalog, including each permission's `scope` and `defaultRoles`, for role editors.

## Checking permissions

```ts
import { AUTHORIZATION_SERVICE } from '@blixis/contracts'

await ctx.services.get(AUTHORIZATION_SERVICE).require({
  actor: ctx.actor,
  action: 'seo.write',
  resource: { type: 'entry', id: entryId, spaceId },
})
```

- `require` throws:
  - `UnauthorizedError` for anonymous actors;
  - `NotFoundError` (named after `resource.type`) when the actor has no membership in the resource's tenant, so its existence isn't revealed;
  - `ForbiddenError` for members without the permission.

  `can` returns a boolean instead.
- Unknown permission IDs, or a resource without the tenant IDs the permission's scope needs, throw `ModuleError`. These are bugs, not denials.
- Check permissions **in services**, not in route handlers, so REST, GraphQL, and background jobs share the same rules.
- Always pass the tenant (`spaceId` / `organizationId`) in the [`ResourceRef`](/api/contracts/interfaces/resourceref/). Never trust a resource ID alone.
- Never compare role names in code. Roles are configuration; permissions are the contract.

## How a check is evaluated

`@blixis/permissions` implements `AUTHORIZATION_SERVICE`. It denies by default:

| Actor | Permissions |
|---|---|
| `user` | Space permission: organization role ∪ space role. Organization permission: organization role only. |
| `apiToken` | the owner's permissions ∩ the token's `scopes`. A token without scopes can do nothing. |
| `deliveryKey` | none yet (content delivery, plan 012) |
| `system` | all, but only when the call passes `allowSystem: true` |
| `anonymous` | none |

Memberships and custom roles are loaded once per request. Nothing is cached across requests, so a role change applies to the next request. Each decision is logged at `debug` level (`authorization`, with actor, action and decision).

When a request is bound to a tenant (`spaceScoped()`), a resource from another tenant is denied too.

## Managing roles

| Route | Permission |
|---|---|
| `GET /api/v1/permissions` | signed in |
| `GET /api/v1/organizations/:orgId/roles` | `roles.read` |
| `POST /api/v1/organizations/:orgId/roles` | `roles.manage` |
| `PATCH`/`DELETE /api/v1/organizations/:orgId/roles/:roleId` | `roles.manage` |

**Escalation guard:** creating, changing, deleting or granting a role requires holding every permission in it. So an admin can't create a role with `organizations.owners.manage` and can't grant `owner`. Only owners hold every permission. System roles can't be changed, and a custom role can't be deleted while a membership uses it.
