`@blixis/auth` answers **who is calling** (ADR 0009). What they may do is authorization, handled by `@blixis/permissions` (see [Actors and permissions](/concepts/permissions/)).

## How clients authenticate

| Step | Endpoint | Result |
|---|---|---|
| Sign in | `POST /api/v1/auth/sign-in` with `{ email, password }` | An **access token** (JWT, 15 min) in the body. The **refresh token** comes in an `HttpOnly` cookie, or in the body with `"tokenDelivery": "body"` for non-browser clients |
| Call the API | `Authorization: Bearer <accessToken>` | Your routes see a `user` actor |
| Refresh | `POST /api/v1/auth/refresh` (cookie, or `{ refreshToken }`) | A new access token plus a **new** refresh token. The old refresh token is used up |
| Sign out | `POST /api/v1/auth/sign-out` | The refresh-token family is revoked and the cookie cleared |
| Public keys | `GET /api/v1/auth/jwks` | Ed25519 public keys, for verifying tokens elsewhere |

- **Refresh tokens rotate on every use.** If an old, already-used refresh token shows up again, Blixis assumes it was stolen and revokes the whole family, which signs that device out.
- **Access tokens can't be revoked.** They expire after at most 15 minutes, so keep them in memory, never in `localStorage`.
- **Cookie-based refresh and sign-out** only accept requests from allowed origins (`AUTH_ALLOWED_ORIGINS`). This protects them against CSRF.

<Aside type="note">
Public sign-up is **off** by default (`authModule({ allowSignUp: true })` turns it on). Create the first user with the CLI:

```bash
read -rs "AUTH_PASSWORD?Password: "; export AUTH_PASSWORD; echo
DATABASE_URL=… pnpm auth:create-user --email you@example.com --name "Your Name"
unset AUTH_PASSWORD
```
</Aside>

## Personal API tokens

For scripts, CI, and integrations, create a long-lived token instead of storing a password:

| Endpoint | Does |
|---|---|
| `POST /api/v1/auth/tokens` with `{ name, scopes?, expiresInDays? }` | Returns `{ id, name, prefix, scopes, expiresAt, token }`. The `token` (`blx_pat_…`) is shown **only this once** |
| `GET /api/v1/auth/tokens` | Your active tokens: name, prefix, scopes, expiry, last use. Never the secret |
| `DELETE /api/v1/auth/tokens/:id` | Revokes it immediately |

Use a token as `Authorization: Bearer blx_pat_…`. Your routes then see `{ type: 'apiToken', tokenId, ownerId, scopes }`.

- **Management needs a real sign-in** with a live session. API tokens cannot create or revoke tokens (`403`), and a signed-out session can't use its remaining access token for this.
- **Scopes** must be permission IDs that modules register (`GET /api/v1/permissions`). A token can do what its owner can do **and** its scopes allow. A token without scopes can do nothing, and API tokens can't create organizations.
- **Revocation:** a revoked or expired token gets `401` straight away. Disabling a user revokes all of their API tokens and signs them out everywhere, through the `user.disabled` event.
- **Storage:** only a SHA-256 hash is stored, together with a short prefix so you can recognise the token.

## Passwords

Passwords must be 12 to 256 characters and not on a list of common passwords. There are no composition rules; this follows NIST SP 800-63B. They are hashed with **scrypt** (32 MiB, about 90 ms). Error messages never reveal whether an email exists, and an unknown email takes as long to reject as a wrong password.

## Brute-force protection

Failed sign-ins are counted per email and per client IP (`CF-Connecting-IP`) over 15 minutes:
- **Limits:** after 5 failures for an email, or 30 for an IP, sign-in answers `429 Too Many Requests` with `Retry-After`, even for the correct password.
- **Backoff:** the lock starts at 1 minute and doubles with every further failure, up to 1 hour.
- **Reset:** a successful sign-in resets the email's counter.
- **No enumeration:** unknown emails are counted the same way, so a lock never reveals whether an account exists.

Counters live in Postgres as hashes (`auth.sign_in_throttle`). Tune them with `authModule({ throttle: { … } })`.

## In your module

Read the caller from the request context. Never read tokens or cookies yourself:

```ts
routes.get('/mine', async (c) => {
  const actor = c.var.requestContext.actor
  if (actor.type !== 'user') throw new UnauthorizedError('Sign in first')
  return c.json(await listFor(actor.userId))
})
```

Profiles live in `@blixis/users`: `c.var.services.get(USER_SERVICE).getById(actor.userId)`, or `GET /api/v1/users/me`.

## Operations

- **Signing keys:** the `AUTH_SIGNING_KEYS` Worker secret holds a JSON array of Ed25519 private JWKs. `pnpm auth:generate-key` creates one. To rotate, put a new key first and remove the old one after 15 minutes.
- **Cleanup:** expired refresh tokens are deleted by the minute cron.
