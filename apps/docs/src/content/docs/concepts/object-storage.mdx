Modules store binaries (uploads, imports, exports, generated files) through **one port**, [`ObjectStorage`](/api/contracts/interfaces/objectstorage/) from `@blixis/contracts`, resolved with the [`OBJECT_STORAGE`](/api/contracts/variables/object_storage/) token. The API Worker provides it on its R2 bucket; tests use an in-memory fake. Your module never depends on Cloudflare. See [ADR 0013](https://github.com/blixis-io/monorepo/blob/main/docs/decisions/0013-asset-uploads.md).

## Rules

- **Postgres is the record, storage holds bytes.** Keep everything that matters (name, type, size, owner, tenant) in your tables. Object metadata is never the source of truth.
- **Choose opaque, tenant-prefixed keys:** `<spaceId>/<yourId>/<fileId>`. Never build keys from user input such as file names.
- **Write each key once.** To replace a file, write a new key and delete the old one after your transaction commits (in an event consumer). A rolled-back change then never loses a file, and URLs to a key can be cached forever.
- **Stream, don't buffer.** A Worker isolate has 128 MB for all its requests. Pass `request.body` and its `size` straight to `put`.

## Use it

```ts
import { OBJECT_STORAGE } from '@blixis/contracts'
import { newId } from '@blixis/shared'

const storage = services.get(OBJECT_STORAGE)
const key = `${spaceId}/${exportId}/${newId()}`
const size = Number(request.headers.get('content-length'))
const stored = await storage.put(key, request.body, { size, contentType: 'text/csv' })
// stored.size and stored.etag are what the storage measured — save them in your table.

const file = await storage.get(key, { range: { offset: 0, length: 1024 } })
if (file !== undefined) return new Response(file.body, { status: 206 })
```

| Method | What it does |
|---|---|
| `put(key, body, { size, contentType, sha256 })` | Stores a stream, buffer or string. With `sha256` (hex), a mismatch stores nothing and throws `ValidationError` |
| `get(key, { range })` / `head(key)` | Bytes (optionally a range: `{ offset, length }` or `{ suffix }`) or metadata; `undefined` if missing |
| `delete(keys)` | One key or many; missing keys are ignored, so retries are safe |
| `list(prefix, { cursor, limit })` | Keys under a prefix, a page at a time |
| `createMultipart` · `uploadPart` · `completeMultipart` · `abortMultipart` | Large files in parts: every part but the last the same size, at least 5 MiB, up to 10 000 parts |

<Aside>
`OBJECT_STORAGE` is optional: an app that stores no files doesn't provide it. Use `services.getOptional(OBJECT_STORAGE)` if your module works without it, or declare the dependency in your module's documentation.
</Aside>

## In the API Worker

`r2StorageModule()` from `@blixis/cloudflare` provides `OBJECT_STORAGE` on the `ASSETS` R2 bucket binding (`r2StorageModule({ binding })` for another bucket). The adapter streams bodies, maps checksum and length mismatches to `ValidationError`, and treats a missing multipart upload as `NotFoundError`.

## In tests

```ts
import { OBJECT_STORAGE } from '@blixis/contracts'
import { createMemoryObjectStorage, createTestBlixis, serviceOverride } from '@blixis/testing'

const storage = createMemoryObjectStorage()
const t = await createTestBlixis({
  modules: [exportsModule()],
  overrides: [serviceOverride(OBJECT_STORAGE, storage)],
})
// … run the feature, then inspect:
expect(storage.keys()).toHaveLength(1)
expect(storage.text(storage.keys()[0] ?? '')).toContain('title,slug')
```

The fake enforces the same rules as R2 (checksums, declared sizes, multipart part sizes), so a test that passes against it won't fail on R2 for those reasons. Pass `createMemoryObjectStorage({ minPartBytes: 4 })` to test multipart flows with small parts.
