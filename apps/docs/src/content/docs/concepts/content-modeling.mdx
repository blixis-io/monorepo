A **content model** describes what editors can create. In Blixis it consists of **content types**, **components**, and their **fields**. Models belong to one environment of a space (`main` by default). The storage model is recorded in [ADR 0010](https://github.com/blixis-io/monorepo/blob/main/docs/decisions/0010-content-storage-model.md).

```text
Space "Website"
└─ Environment "main"
   ├─ Content type  page        title · slug · body (blocks) · seo fields
   ├─ Content type  blogPost    title · author (reference) · content (rich text)
   ├─ Component     hero        heading · image · button (link)
   ├─ Component     section     title · text (rich text) · children (blocks)
   └─ Component     faqList     items (blocks of faqItem)
```

## Content types and components

Every type has a `kind`:

| Kind | What it is | Examples |
|---|---|---|
| `entry` | Something editors create, publish, and link to. Entries have their own lifecycle (plan 011). | page, blog post, author, product |
| `component` | A reusable building block that only exists **inside** another entry, in a `blocks` field. It is saved, published, and translated together with that entry. | hero, text section, image gallery, FAQ item, call to action |

Use a **component** when the block has no life of its own. A hero belongs to one page, so it should be edited and published with that page.

Use a **reference** to an entry when the content is shared or has its own lifecycle. An author appears on many posts; a product has its own page.

Components can contain `blocks` fields too, so sections can hold columns and columns can hold cards. Nesting goes at most **5 levels** deep.

## Fields

Each field has these properties:

| Property | Meaning |
|---|---|
| `id` | Stable 8-character id, generated by Blixis. Stored data is keyed by it, so renames never touch content. |
| `apiId` | The name clients use, e.g. `metaTitle`. It is camelCase, unique within the type, and can be renamed at any time. `id`, `sys`, `type`, and names starting with `_` are reserved. |
| `name` | The label editors see. |
| `type` | One of the [field types](/content/field-types/), e.g. `text`, `richText`, `blocks`, or a module's `acme.color`. |
| `required` | Must have a value when publishing. Drafts may be incomplete. |
| `localized` | One value per locale instead of one value. |
| `settings` | Type-specific options such as `maxLength`, `options` or `componentIds`. They're validated, and defaults are filled in. |
| `description` | Help text for editors. |
| `group` | The editor tab, one of the type's `groups`. |
| `hidden` | Hidden in editors, still part of the API. |
| `showWhen` | Show the field only while a sibling field has a value, e.g. `{ "field": "hasButton", "equals": true }`. |
| `disabled` | Retired: left out of APIs and validation, but kept in stored versions. |

A type can also name a **`displayField`**, a text field used as an entry's title in lists, and define **`groups`**, the editor tabs such as `{ "id": "seo", "name": "SEO" }`.

## Localization

Localization is set per field:

```json
{
  "title": { "en-US": "Welcome", "nl-NL": "Welkom" },
  "slug": "welcome",
  "body": { "en-US": [ … ], "nl-NL": [ … ] }
}
```

- A **localized** field takes a map from the space's locale codes to values. A missing locale falls back along the space's fallback chain when content is read.
- A **non-localized** field takes the plain value, shared by all locales.
- **Component fields are never localized on their own.** Localize the `blocks` field that contains them: each locale then has its own list of blocks, so a Dutch page can have different sections than the English one.

## Validation

Entries are validated against their content type in two modes:

| Mode | When | Checks |
|---|---|---|
| `draft` | saving | types, formats, allowed values, unknown fields |
| `publish` | publishing | everything above, plus `required` fields (for localized fields: the default locale) and minimum item counts |

A field hidden by `showWhen` is **not required** while its condition is false. If it still has a value, the value is type-checked.

Errors point at the exact value, even deep inside blocks:

```json
{ "path": ["fields", "body", "en-US", 1, "children", 0, "heading"], "message": "Required" }
```

The same validator is used by REST, GraphQL, imports and queue consumers. Modules can use it too, through `compileEntrySchema()` from `@blixis/content`.

## Changing a model safely

Every change increments the type's `version`. Send the version you edited in each `PATCH`: if someone else changed the type in the meantime, you get `409` instead of overwriting their work.

| Change | Allowed? |
|---|---|
| Add a field, rename `apiId` or `name`, reorder, change help text, groups or presentation | Always |
| Change `required` or settings (e.g. a shorter `maxLength`) | Always. Existing entries are checked again on their next save or publish |
| Change a field's `type` or `localized` | Only while the type has no entries |
| Remove a field | While entries exist, set `"disabled": true` first, then remove it in a later change |
| Change `kind` | Only without entries, and while no other type uses it |
| Delete a type | Only without entries, and while no other type uses it |

<Aside type="tip">
Renaming is safe because stored content uses stable ids. Clients see the new `apiId` right after the change; update your frontend queries at the same time.
</Aside>

## Permissions and events

| Permission | Default roles | Grants |
|---|---|---|
| `content.types.read` | admin, editor, viewer | list and read types and components |
| `content.types.write` | admin | create, change, delete |

Changes emit `content-type.created`, `content-type.updated` (with the new `version`) and `content-type.deleted`. Delivery caches and webhooks subscribe to these.
