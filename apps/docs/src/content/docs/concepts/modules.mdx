A module is a plain object implementing [`BlixisModule`](/api/contracts/interfaces/blixismodule/), usually returned by a **factory** that module packages default-export. The same contract applies to first-party and third-party modules.

## Anatomy

| Field | Purpose |
|---|---|
| `meta` | [`ModuleMeta`](/api/contracts/interfaces/modulemeta/): `name` (package name), `version`, optional `requires` (package → semver range), `capabilities`, `requiresCapabilities` |
| `config` / `configSchema` | Raw options from the factory and the schema that validates them |
| `setup(ctx)` | Register services; runs once during bootstrap |
| `boot(ctx)` | Runs once, lazily, before the first request or event |
| `rest` | A Hono app mounted at `/api/v1${path}` |
| `graphql` | Schema fragment (`typeDefs`) and resolvers merged into `/graphql` |
| `permissions` | [Permission definitions](/concepts/permissions/) your services check |
| `events` | [Event subscriptions](/concepts/events/) |
| `migrations` | [Module-owned migrations](/concepts/context-and-migrations/#migrations) |

## Factories

```ts
import type { ModuleFactory } from '@blixis/contracts'

// No options: () => BlixisModule
const content: ModuleFactory = () => ({ meta: { name: '@blixis/content', version: '0.1.0' } })

// With options: (options?) => BlixisModule<Config>
const seo: ModuleFactory<{ defaultTitle?: string }, { defaultTitle: string }> = (options = {}) => ({
  meta: { name: '@acme/blixis-seo', version: '1.0.0' },
  config: options,
  configSchema: SeoConfig,
})
```

Consumers always call the factory in the composition root: `modules: [content(), seo({ defaultTitle: 'x' })]`.

### `defineModule`

[`defineModule`](/api/kernel/functions/definemodule/) from `@blixis/kernel` is a convenience that always returns a factory and infers the types for you:

```ts
import { defineModule } from '@blixis/kernel'

// Without options → content()
export default defineModule({ meta: { name: '@blixis/content', version: '1.0.0' } })

// With options → seo({ defaultTitle: 'Home' }); ctx.config is typed from configSchema
export default defineModule((options: { defaultTitle?: string }) => ({
  meta: { name: '@acme/blixis-seo', version: '1.0.0' },
  config: options,
  configSchema: SeoConfig,
}))
```

It freezes the returned module and registers nothing globally. Third-party modules may use it (add `@blixis/kernel` as a peer dependency) or write the factory by hand against `@blixis/contracts` only.

## Lifecycle

```text
define → validate → setup (register) → boot (lazy) → ready
```

- **Validate:** the kernel checks the whole module graph — duplicate names, versions, missing packages or capabilities, route and service conflicts, invalid configuration. It throws one [`ModuleValidationError`](/api/kernel/classes/modulevalidationerror/) listing **every** problem, each prefixed with the module name:

  ```text
  Invalid module configuration (2 problem(s)):
    - [@acme/blixis-seo] requires capability blixis.content, which no registered module provides
    - [@acme/blixis-seo] requires @blixis/kernel@^2.0.0, but 1.4.0 is registered
  ```

  Modules are then set up in dependency order: required packages and capability providers first, otherwise in the order you registered them.
- **`setup`** receives a [`ModuleSetupContext`](/api/contracts/interfaces/modulesetupcontext/) with `config`, `services` (provide + get), `logger`, and `meta`.
- **`boot`** receives a [`ModuleBootContext`](/api/contracts/interfaces/modulebootcontext/) with read-only `services`, `logger`, and all registered `modules`.

<Aside type="caution" title="No I/O in setup">
Cloudflare Workers forbid I/O while the Worker script is being initialised. Do not open connections or fetch anything in `setup`; use request-scoped services or `boot`.
</Aside>

## Composing an application

The app's composition root lists modules explicitly and hands them to [`createBlixis`](/api/kernel/functions/createblixis/):

```ts
import { createBlixis } from '@blixis/kernel'
import { modules } from './blixis.config.ts'

const app = createBlixis({ modules })   // validates the module graph immediately
export default app                      // app.fetch handles requests
```

`createBlixis` is synchronous and safe at the top level of a Worker. Your `setup` and `boot` hooks run the first time the app handles a request (`app.ready()` runs them explicitly, e.g. in tests):

- `setup` hooks run once, in bootstrap order. If one throws, startup fails with `[your-module] setup failed: …` and stays failed — it is a configuration error.
- `boot` hooks run once after all setups. If one throws, the next request retries from that module.

## Configuration

Put the factory's options in `config` and describe them with `configSchema` (any [Standard Schema](/concepts/validation/), e.g. Zod). The kernel validates `config` and passes the **schema output** — defaults applied — to `setup` as `ctx.config`. Invalid configuration stops startup with an error naming your module.

The kernel validates every module's configuration **before the first `setup` runs** and reports all problems at once. Messages contain the path and the problem, never the value (configuration may contain secrets):

```text
Invalid module configuration (1 problem(s)):
  - [@acme/blixis-seo] invalid configuration at config.maxLength: Too small: expected number to be >0
```

A module without `configSchema` receives its raw `config` (typed `unknown`).

## REST routes

```ts
import type { ModuleHonoEnv } from '@blixis/contracts'
import { Hono } from 'hono'

export const routes = new Hono<ModuleHonoEnv>().get('/:id', (c) => {
  const ctx = c.var.requestContext // RequestContext: actor, tenant, logger, services…
  return c.json({ requestId: ctx.requestId })
})
// module: rest: { path: '/seo', app: routes }  →  GET /api/v1/seo/:id
```

- [`ModuleHonoEnv`](/api/contracts/interfaces/modulehonoenv/) exposes `requestContext` and `services` on `c.var`. There are **no bindings**: modules never access Cloudflare `env`.
- A Hono app declared with a different environment is rejected at compile time.
- Keep handlers thin: parse and validate input, call a service, map the result. Throw [public errors](/concepts/errors/); the kernel turns them into [problem details](/concepts/errors/#what-clients-receive-rest) responses.
- Every request gets a fresh [request scope](/concepts/services-and-capabilities/#scopes) and an `x-request-id` / `x-correlation-id` response header. A valid incoming `x-correlation-id` is kept, so you can trace calls across services.
- Two modules may share a prefix (e.g. `/spaces`), but registering the **same method and path** twice fails startup, naming both modules.
- `GET /api/v1/health` is reserved by the kernel: a liveness check that answers even before modules have booted.

## GraphQL

```ts
graphql: {
  typeDefs: 'extend type Entry { seoTitle: String }',
  resolvers: { Entry: { seoTitle: (entry) => lookupTitle(entry) } },
}
```

The platform composes all fragments into one schema at `/graphql`. Modules never create their own GraphQL server. Resolvers call services, like REST handlers.
